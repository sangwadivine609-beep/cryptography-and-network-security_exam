\section{Introduction}
%======================================================================
This project addresses the security of a central student-records system.
The scenario involves a records server accessed by authorised staff across
campuses. The work is organised in three parts:

\begin{enumerate}[leftmargin=*]
  \item a \textbf{risk assessment} identifying assets, vulnerabilities,
        consequences, a risk ranking and recommended controls;
  \item a \textbf{Python security tool} that encrypts and decrypts a sample
        student record, verifies file integrity with SHA-256, and handles errors
        gracefully;
  \item a \textbf{network traffic filtering} design with a firewall policy
        and three documented tests.
\end{enumerate}

\subsection{Objectives}
\begin{itemize}[leftmargin=*]
  \item Identify and rank the main security risks to the student-records system.
  \item Protect the confidentiality of a student record through symmetric encryption.
  \item Detect unauthorised modification of a file through cryptographic hashing.
  \item Restrict network access to the records server using a default-deny firewall policy.
\end{itemize}

\section{Encryption and Integrity Tool}\label{sec:tool}
%======================================================================

\subsection{Design Overview}
The tool \texttt{security\_tool.py} is a command-line program written in Python 3.
It uses the \texttt{cryptography} library's \textbf{Fernet} scheme for encryption
and Python's standard \texttt{hashlib} module for SHA-256 hashing.

Fernet provides authenticated symmetric encryption: it combines AES-128 in CBC mode
for confidentiality with an HMAC-SHA256 tag for authenticity. A modified or
corrupted ciphertext, or a wrong key, is therefore detected at decryption time and
raises an \texttt{InvalidToken} exception rather than returning garbage data.

\subsection{Commands}
\begin{table}[h!]
\centering
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{@{}l p{10.5cm}@{}}
\toprule
\textbf{Command} & \textbf{Purpose} \\
\midrule
\texttt{python security\_tool.py key}     & Generate the Fernet key outside the repository. \\
\texttt{python security\_tool.py encrypt} & Encrypt \texttt{student\_record.txt} to \texttt{student\_record.enc}. \\
\texttt{python security\_tool.py decrypt} & Decrypt the file and compare it with the original. \\
\texttt{python security\_tool.py hash}    & Compute and save the SHA-256 baseline. \\
\texttt{python security\_tool.py verify}  & Compare the current SHA-256 with the saved baseline. \\
\texttt{python security\_tool.py help}    & Display usage information. \\
\bottomrule
\end{tabular}
\caption{Command-line interface.}
\end{table}

\subsection{Key Management}
A key stored next to the data it protects offers little security. The tool
therefore saves \texttt{encryption.key} in the \textbf{parent directory} of the
project, outside the Git repository, so that it cannot be committed by accident.
Key generation refuses to overwrite an existing key, preventing accidental loss of
access to previously encrypted data.

\begin{lstlisting}[language=Python,caption={Key location and generation (excerpt).}]
BASE_DIR   = os.path.dirname(os.path.abspath(__file__))
PARENT_DIR = os.path.dirname(BASE_DIR)
KEY_FILE   = os.path.join(PARENT_DIR, "encryption.key")

def generate_key():
    if os.path.exists(KEY_FILE):
        print(f"Key already exists: {KEY_FILE}")
        print("No new key was generated.")
        return
    key = Fernet.generate_key()
    with open(KEY_FILE, "wb") as file:
        file.write(key)
\end{lstlisting}

\subsection{Encryption and Decryption}
Encryption reads the plaintext record in binary mode, encrypts it with the Fernet
cipher and writes the result to \texttt{student\_record.enc}. Decryption reverses
the process, writes \texttt{student\_record\_decrypted.txt}, and then compares the
decrypted bytes with the original file, reporting whether verification succeeded.

\begin{lstlisting}[language=Python,caption={Decryption with error handling (excerpt).}]
try:
    decrypted = cipher.decrypt(encrypted)
except InvalidToken as error:
    raise ValueError(
        "Decryption failed: invalid key or corrupted encrypted data."
    ) from error

# ... write decrypted file, read original ...
if decrypted == original:
    print("Decryption successful.")
    print("Verification successful: decrypted content matches the original.")
else:
    print("Decryption completed, but verification FAILED.")
\end{lstlisting}

\subsection{SHA-256 Integrity Verification}
The \texttt{hash} command computes the SHA-256 digest of the record and stores it as
a baseline. The \texttt{verify} command recomputes the digest and compares it to the
stored value. Any change to the file, even a single bit, produces a completely
different digest, so tampering is detected. The file is read in 4096-byte chunks,
so the function works for large files without loading them entirely into memory.

\begin{lstlisting}[language=Python,caption={SHA-256 of a file.}]
def sha256_file(filename):
    if not os.path.exists(filename):
        raise FileNotFoundError(f"File not found: {filename}")
    digest = hashlib.sha256()
    with open(filename, "rb") as file:
        for chunk in iter(lambda: file.read(4096), b""):
            digest.update(chunk)
    return digest.hexdigest()
\end{lstlisting}

\subsection{Error Handling}
The tool anticipates the following failure conditions and reports each with a clear
message and a non-zero exit code instead of a stack trace.

\begin{table}[h!]
\centering
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{@{}p{5.5cm} p{9cm}@{}}
\toprule
\textbf{Condition} & \textbf{Behaviour} \\
\midrule
Missing key file & Error message with the command needed to generate a key. \\
Missing input or encrypted file & \texttt{FileNotFoundError} caught and reported. \\
Wrong key or corrupted ciphertext & \texttt{InvalidToken} converted to a readable error. \\
Invalid key contents & \texttt{ValueError} reported as ``Invalid encryption key''. \\

\end{table}

\subsection{Firewall Policy}
The design follows the \textit{default deny} principle: everything not explicitly
permitted is dropped. This directly implements the ``firewall rules and network
segmentation'' control from the risk assessment.

\begin{table}[h!]
\centering
\renewcommand{\arraystretch}{1.3}
\begin{tabular}{@{}c p{10.5cm}@{}}
\toprule
\textbf{Rule} & \textbf{Description} \\
\midrule
1 & Allow established and related connections. \\
2 & \textbf{DROP} all traffic from the guest network \texttt{192.168.2.0/24} to the records server \texttt{192.168.1.70}. \\
3 & \textbf{ACCEPT} TCP traffic from the staff network \texttt{192.168.1.0/24} to \texttt{192.168.1.70} on port \texttt{8443}. \\
4 & \textbf{DROP} TCP traffic to port \texttt{8443} from sources outside the authorised staff network. \\
5 & \textbf{DROP} all other inbound traffic (default policy). \\
\bottomrule
\end{tabular}
\caption{Firewall rules (default policy: DROP).}
\end{table}

Rule 2 is placed before the ACCEPT rule so that guest traffic is dropped explicitly
and cannot be matched by a broader permit rule. The Linux \texttt{iptables}
equivalent of this policy is provided in \texttt{firewall\_rules.sh}.

\subsection{Testing Method}
The tests were run with \texttt{firewall\_simulator.py} on Windows~11. Because no
separate guest network was available on the test computer, the guest network was
\emph{simulated}. The \texttt{iptables} script was written for Linux and was
therefore documented but not executed on Windows~11.

\subsection{Limitations}
\begin{itemize}[leftmargin=*]
  \item The firewall tests used a simulator on Windows~11 and a simulated guest
        network; results confirm the rule logic but not behaviour on real
        hardware or a live \texttt{iptables} deployment.
  \item Fernet is a symmetric scheme, so secure key distribution and storage remain
        the operator's responsibility. Storing the key one directory above the
        repository prevents accidental commits but is not a substitute for a
        hardware security module or a managed secrets store.
  \item The SHA-256 baseline is stored in a file that an attacker with write
        access could also modify. For stronger assurance the baseline should be
        protected separately or replaced by an HMAC or digital signature.
  \item The tool handles a single sample record; a production system would need
        access control, auditing and key rotation.
\end{itemize}

\subsection{Possible Improvements}
\begin{itemize}[leftmargin=*]
  \item Password-derived keys (e.g.\ PBKDF2 or scrypt) or an external key vault.
  \item Multi-factor authentication for staff accounts.
  \item TLS for all traffic to port 8443, so data is protected in transit as well as at rest.
  \item Logging of dropped packets and periodic automated integrity checks.
\end{itemize}

%======================================================================
\section{Conclusion}
%======================================================================
The project delivers a coherent security solution for the student-records scenario.
The risk assessment identified weak passwords, unencrypted transfers and guest
network exposure as the key threats. The Python tool protects record
confidentiality with authenticated encryption and detects modification with SHA-256
verification, while handling errors safely. The default-deny firewall policy
isolates the records server, and all three tests behaved as expected. Together,
these measures reduce the highest-ranked risks, and the limitations identified above
point to clear next steps for a production deployment.
